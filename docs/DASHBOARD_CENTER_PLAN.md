# Dashboard Center — plan and gap analysis

Started 2026-09-30. This is a large, multi-session build (the user's own spec has 33 sections and a 12-phase order) — this doc is the durable reference so a future session doesn't re-derive the architecture research from scratch. Read this before touching any `/dashboards/*` page or the Dashboard Center nav group in `sidebar-nav.tsx`.

**IA decision:** Dashboard Center is a **new, separate** top-level nav group, not a replacement for the existing `/overview` page or any existing per-module page (`/leads`, `/analytics`, `/upwork/*`, etc.). It reuses real endpoints/services wherever they exist rather than duplicating them. Meta Ads' nav entry inside Dashboard Center links straight at the already-built `/meta-ads` dashboard rather than a second copy.

**Reusable code — extend, don't duplicate:**
- `apps/api/src/analytics/date-range.ts` (`resolveDateRange`, `DateRangeName`) — already implements TODAY/YESTERDAY/THIS_WEEK/LAST_WEEK/THIS_MONTH/LAST_MONTH/LAST_30_DAYS/LAST_90_DAYS/CUSTOM/ALL_TIME. Needs THIS_QUARTER/THIS_YEAR added for the Dashboard Center's own preset list (`apps/web/components/dashboard-center/date-range-bar.tsx`).
- `apps/api/src/analytics/analytics.math.ts` (`rate()`, `buildPerformance()`) — already implements the exact delivery/open/click/reply/meeting/conversion-rate formulas the spec asks for, with safe zero-division. Reuse directly for the Email Campaign Dashboard.
- `apps/web/components/chart-kit.tsx` — shared chart chrome (SERIES colors, ChartWithTable, DataTable, StatTile) used by Meta Ads; reuse for every new dashboard.

## Gap analysis (2026-09-30 research pass) — what's real vs. what would be fabricated

**Leads:** Good data — `Lead.filterId`→`NicheFilter` is a real relation (not free text), `LeadImport` tracks batch upload attribution, two-tier dedup already exists (DB unique constraints + fuzzy name/LinkedIn-slug matching, see `dedup.spec.ts`). `Lead.assignedUserId` exists in schema but **no endpoint ever writes it** — use `uploadedByUserId` for "who added this lead" instead. **Missing: no stage-transition history** — `PipelineState` stores only current stage + one prior stage, not a full log. "Average time in stage" / historical stage funnels need a new `LeadStageHistory` table (leadId, fromStage, toStage, changedByUserId, changedAt), written at every stage-change call in `leads.service.ts`. This same gap blocks the Pipeline Dashboard.

**Email Campaigns:** Best-covered domain. `EmailEventType` enum is already per-message, timestamped, granular (QUEUED/SENT/DELIVERED/OPENED/CLICKED/REPLIED/BOUNCED/SPAM_COMPLAINT/UNSUBSCRIBED/BLOCKED/FAILED). `SendingSession` **is** the "queue" concept the spec asks for (no separate named-queue entity needed). `EmailMessage.sequenceStep` (1-5) is the stage. Stage-to-stage funnel and day/hour response-timing aggregations aren't built yet but are straightforwardly computable from existing rows — no new tables needed.

**Unified Inbox:** `InboundEmailThread`/`InboundEmailMessage` solid. **No dedicated "website form submission" model exists** — `email-lead-classifier.service.ts` only tags/classifies inbound email, doesn't distinguish a contact-form email from any other inbound lead-candidate, and captures no form-name/source-page fields. Show "Data unavailable" for per-form breakdowns unless that capture is added at ingestion.

**Social Inbox:** `SocialConversation.assignedToUserId`/`SocialMessage.sentAt`+`fromUs` make per-user response time computable. **No link from a social conversation/comment to a `Lead` anywhere** — the schema's own comment at the Social Hub section explicitly calls this "an explicit later-phase decision." The spec's "message → lead → client" funnel is **not buildable today**; must render as unavailable, not guessed.

**Upwork — the biggest gap:** `UpworkProposal.connects` is a bare count with **zero cost data anywhere in the schema**. There is no connect-purchase/pricing ledger. Every dollar metric the spec wants (connect cost, cost/bid, cost/client, cost/invite) is **currently uncomputable, honestly or otherwise** — Upwork's per-connect price varies and isn't exposed via API to third parties. Bid/invite count metrics (bids per client, connects per client) work fine today. **Before Phase 6 can show real $ figures, needs a new `UpworkConnectPurchase` model (orgId, purchasedAt, connectsAmount, totalCost, currency) — populated by manual entry**, since there's no API to pull it from. This is a real workflow addition (someone has to type in each connect purchase), not just a backend detail — confirm with the user before building it. Also: `UpworkProposal.submittedBy`/`closedBy` are **plain strings, not `User` relations** (schema comment confirms this is deliberate, to not force a login for every submitter) — per-user Upwork rollups group on free text, which can fragment on typos/casing.

**Meta Ads:** Built this session. **No FK from an ad's reported "lead" action-count to an actual `Lead` row** — attribution stops at raw ad metrics. Qualified Lead → Meeting → Client funnel stages are not computable without a UTM/webhook-based join that doesn't exist yet.

**Team Performance:** Real `User` FKs exist for leads (`uploadedByUserId`), social (`assignedToUserId` on conversations/comments), audit (`actorId`), LinkedIn activity, review notes. Upwork's free-text submitter is the flagged risk (above). **Email sending has no per-user attribution field at all** — an `EmailMessage` belongs to a `Lead`, not a sending user — crediting a team member for email performance needs a real modeling decision (e.g. campaign owner? whoever uploaded the lead?), not just a query.

**Activity/Audit:** `AuditLog` has a good shape (actorId, entityType/entityId, action, diff, metadata) but **write coverage is narrow** — grepped confirmed only 4 call sites (auth login/logout, permission-denial-logger, users.service team management, and a generic interceptor that only fires on POST/PATCH/DELETE routes **with an `:id` URL param**, which misses nearly every creation endpoint: lead create/import/bulk actions, campaign CRUD, email-account CRUD, Upwork proposal CRUD, Meta Ads connect). **Phase 10 is not "build a UI over existing data"** — it needs real `auditLog.write()` calls added at every currently-uncovered creation/bulk-action endpoint first, or the dashboard would understate real activity.

**Benchmarks:** `Organization.settings Json` exists but every other configurable/schedule-like feature in this codebase (`NicheFilter.scheduleCron`, `SendingSchedule`) uses a dedicated typed model instead of the JSON blob — same precedent argues for a real `Benchmark`/`AlertRule` model, not stuffing thresholds into `settings`.

**Attribution:** No first-touch vs. latest-touch distinction anywhere — `Lead.sourceLayer`/`filterId`/`campaignId` are set once at creation and never changed (per the schema's own comment), which makes first-touch at least stable, but there's no separate "conversion source" field and no multi-touch modeling across Email→Social→Upwork. Real net-new modeling work if the user wants this beyond first-touch-only.

## Phase status

- **Phase 1 (shell + nav):** Done 2026-09-30. New "Dashboard Center" nav group (separate from `/overview`), 8 placeholder pages (`/dashboards`, `/dashboards/leads`, `/email`, `/inbox`, `/social`, `/upwork`, `/pipeline`, `/team`, `/activity`) each using shared `DashboardCenterShell`/`NotBuiltYet`/`DashboardDateRangeBar` components in `apps/web/components/dashboard-center/`. Every placeholder states plainly what it will read from and, where relevant, which specific gap above blocks it — no fabricated numbers anywhere. Meta Ads nav entry points at the existing `/meta-ads` page, no duplicate.
- **Phases 2-12:** Not started. Build in the user's own specified order (Leads → Email → Inbox → Social → Upwork → Meta Ads extension → Pipeline → Team → Audit → Alerts/Benchmarks/Data-quality → Performance/exports/RBAC). Each phase should re-read its gap-analysis section above before writing queries, and explicitly decide per-metric whether to build it, or render "Data unavailable" with the reason.

## Open decisions for the user (don't assume)

1. **Upwork connect-purchase ledger**: build a manual-entry UI for recording each connect purchase (amount, cost, date)? Without it, every Upwork dollar metric in the spec stays unavailable.
2. **Social/Meta Ads → Lead linkage**: worth building now (real scope: webhook or manual "convert to lead" linking), or accept those funnels stop at raw channel metrics for now?
3. **Audit log coverage**: Phase 10 needs `auditLog.write()` added at many currently-silent endpoints — confirm this is in scope before starting, since it touches many existing files across leads/campaigns/email-accounts/upwork/meta-ads modules.
4. **Email team attribution**: which user should get credit for a sent campaign's performance — the lead's `uploadedByUserId`, or a new explicit "campaign owner" concept?
